🔧 Adapting to New Robots

The ODD Observer pipeline is robot and application agnostic at the reasoning level. This guide explains how to apply it to different platforms and domains.

What the Pipeline Expects

Agents work with three sensor modalities:

📷
Camera Images

Forward-facing RGB for environment classification, human/animal detection

📡
LiDAR BEV

Bird's eye view images (occupancy, height, roughness) for obstacle/terrain analysis

🧭
IMU / Motion

Acceleration, angular velocity, orientation for motion state and collision detection

Adaptation Steps

1Prepare Data

Convert your sensor data into the expected directory structure with windowed files. 

my_scenario/
├── index_my_scenario.csv
├── cam_my_scenario_w000.png
├── bev_occupancy_my_scenario_w000.png
├── bev_height_my_scenario_w000.png
├── motion_my_scenario_w000.json
└── ...
2Create Robot Profile

Add a knowledge document describing your robot's specs and typical operating patterns.

Location: docs/agent_knowledge/profiles/ROBOT_<NAME>_PROFILE.md

Include: dimensions, sensors, locomotion type, typical speeds, terrain handling.

3Write ODD Specification

Define your robot's safe operating boundaries in natural language.

The ODD Spec Agent parses this into structured axes for compliance checking.

4Tune Thresholds

Adjust tool parameters for your platform's characteristics.

Collision detection, BEV analysis, and motion thresholds may need calibration.

Writing Effective ODD Specifications

The key to a good ODD spec is clarity and measurability. Agents need concrete thresholds they can evaluate against sensor data.

✅ Good ODD Statements
  • "Maximum speed: 2.5 m/s" — clear threshold
  • "Gentle ramps (<15 degree incline)" — specific angle
  • "Humans within 0.5-1m = OUT OF ODD" — boundary + consequence
  • "Lighting 200-1000 lux; <50 lux = OUT" — range with exclusion
❌ Poor ODD Statements
  • "Normal indoor lighting" — too vague
  • "Don't go too fast" — no threshold
  • "Avoid rough terrain" — undefined roughness
  • "Be careful around people" — no actionable rule
💡 Writing Tips:
  • Use SI units consistently — m/s for speed, m/s² for acceleration, degrees for angles
  • Define both "designed for" AND "not designed for" — explicit negatives help agents identify violations
  • Explain expected behaviors — "Brief acceleration during obstacle avoidance is normal" prevents false positives
  • Use progressive severity: "Designed for" → "Can handle" → "NOT designed for" → "DEFINITELY NOT"

ODD Structure Sections

Follow the structure from odd_agents/odd_definition.py. Each section maps to evaluation axes:

ROBOT PHYSICAL SPECIFICATIONS: Footprint, height, clearance requirements — Used for clearance analysis
ENVIRONMENT: Indoor/outdoor, lighting ranges (in lux), typical conditions — Used for environment classification
OBSTACLE HANDLING: Expected density, navigation constraints — Used for obstacle density evaluation
MOTION CHARACTERISTICS: Max speed (m/s), acceleration (m/s²), pitch/roll limits — Used for motion compliance
TERRAIN: Acceptable surfaces, incline limits, exclusions — Used for traversability assessment
HUMAN/ANIMAL PROXIMITY: Distance thresholds with consequences — Used for safety zone evaluation
DEFINITELY NOT DESIGNED FOR: Hard constraints — Any match = immediate OUT_ODD

Data Format Summary

File Type Format Content
Camera PNG/JPEG Forward-facing RGB, any resolution
BEV Occupancy Grayscale PNG Obstacles only (ground filtered), robot-centered
BEV Height Grayscale PNG Full terrain elevation map
BEV Roughness Grayscale PNG Height variance per cell
Motion JSON Position, orientation, IMU samples, derived_speed
Index CSV Window ID, timestamps, file paths
🔮 Future Architecture

Planned improvements will enable tools to access the knowledge base directly, allowing VLM prompts to automatically incorporate robot profiles and ODD context. This will reduce manual threshold tuning—tools will adapt based on the knowledge layer rather than hardcoded values.

Example: Adapting for a Drone

Data Differences
  • BEV from downward depth/LiDAR instead of outward
  • Roll/pitch can be large (banking maneuvers)
  • Speed range 0-15+ m/s vs 0-3 m/s
  • Altitude becomes a critical ODD axis
ODD Adjustments
  • Add altitude limits (e.g., 5-50m AGL)
  • Include weather constraints (wind, visibility)
  • Define airspace restrictions
  • GPS quality as ODD axis
