ODD Observer for Quadruped Robots

A multi-agent system that reads sensor logs from a Unitree Go2, reconstructs its Current Operating Domain (COD), and determines whether it stayed inside its Operational Design Domain (ODD).

📄 Full technical report (Markdown)  |  📌 Versioning guide

1. Problem Statement

Legged robots like the Unitree Go2 are starting to operate in real indoor spaces such as offices and labs. Safe use requires more than a robot that usually behaves well—we need to know whether it is being used inside the conditions it was actually designed and validated for.

🎯 ODD (Operational Design Domain)

The environment and conditions the robot is designed and validated to operate safely in: indoor, level floors, limited clutter, specific lighting, speed/tilt limits.

📍 COD (Current Operating Domain)

The environment and conditions the robot is actually operating in during a specific run. If COD ⊄ ODD, behavior is no longer guaranteed safe.

In practice, teams have logs, plots, and ad hoc rules, but they don't have a clear end-to-end answer to:

"For this specific run, did the robot stay inside its ODD, and if not—where, when, and by how much did it go out of bounds?"

ODD Observer answers that question. Given a natural language ODD description and a recorded run with camera images, LiDAR BEV images, and IMU data, the system reconstructs the COD, compares it to the ODD, and labels time windows and axes as IN_ODD, BOUNDARY, or OUT_ODD.

2. Why Agents?

The problem naturally breaks into several reasoning tasks:

  • Turn a free-form ODD description into a structured spec with numeric ranges, categories, and rules.
  • Turn raw sensor data (images, BEV, IMU) into semantic descriptions per time window.
  • Aggregate those descriptions into a COD for the run.
  • Compare COD and ODD, generate verdicts, and explain them to a human reviewer.

Each step has different inputs and a different style of reasoning. Treating this as one giant prompt makes it harder to debug and trust. A multi-agent setup works better:

Spec agent → schema-compliant ODD parsing
Perception agent → images + BEV maps
Motion agent → IMU + motion reasoning
Collision agent → proximity + impact detection
Evaluator agent → COD vs ODD comparison
Report agent → clear human summary

This improves traceability. When a window is marked OUT_ODD, we can inspect the artifacts from each agent instead of guessing what happened inside a single black-box call.

3. Architecture

The system is a multi-agent pipeline with a static reporting layer.

Agent Pipeline
Agent Role
ODD Spec Agent Takes natural language ODD → structured spec: numeric ranges (speed, acceleration), categorical limits (environment, clutter, lighting), and flags (stairs allowed?).
Perception Agent Analyzes camera + BEV images per window to estimate environment type, clutter level, corridor width, terrain roughness, and lighting.
Motion Agent Looks at IMU windows to classify motion state (stationary/moving) and estimate acceleration, tilt. Reasons about gravity to avoid confusing static tilt with real motion.
Collision Agent Uses BEV + camera + IMU to estimate distances to obstacles and detect collisions or near-misses. Advisory only—does not affect ODD verdict.
Evaluator Agent Aggregates per-window outputs into a COD description. Compares COD against ODD across all axes and labels each window as IN_ODD, BOUNDARY, or OUT_ODD with severity metrics.
Report Agent Converts evaluator output into a human-facing report with verdict, summary, tables, and recommendations.
Knowledge Layer

Agents share ODD/COD fundamentals (robot-agnostic definitions of what ODD and COD mean) and a Go2 profile (typical indoor operating patterns and thresholds for concepts like "moderate clutter" or "narrow corridor"). This keeps reasoning consistent across runs and agents.

5. Build & Workflow

The project uses:

  • Python for orchestration, data preparation, and tooling.
  • Gemini 2.5 models for all agent reasoning, including multimodal perception.
  • Real and simulated Go2 data: camera images, LiDAR-based BEV images, and IMU streams.
  • Static HTML/JS for reports and dashboards.

The workflow is:

  1. Convert recorded data (ROS bags) into a scenario directory with windowed images, BEV tiles, and IMU slices.
  2. Run the multi-agent pipeline to produce intermediate artifacts and a final JSON result.
  3. Call the reporting script to generate HTML reports.
# Single scenario run python scripts/run_odd_analysis.py # Batch runs python scripts/run_odd_batch_analysis.py # Agent evaluation pytest tests/test_adk_evaluation.py -q

📓 An interactive Jupyter notebook (notebooks/odd_analysis_demo.ipynb) walks through the full pipeline on a sample scenario.

6. Versioning

Because this is safety-related analysis, we track which data and which agent configuration produced each result:

  • Data level: Raw logs and processed scenario directories tracked with explicit data versions and a manifest documenting preprocessing steps.
  • Analysis level: Each run attaches metadata including analysis run ID, ODD description, data version, agent bundle, model names, and Git commit hash.
  • Reporting level: HTML reports surface this metadata so a verdict can be traced back to exact versions.

7. Future Work

🧠 Memory & Retrieval Layer

Finish run-level and ODD-level memory; let agents reference similar past scenarios and aggregated statistics when judging a new run.

🌍 Broader Environment Coverage

More buildings, lighting conditions, clutter patterns, and edge features (stairs, ramps, glass surfaces).

📊 Operator Dashboard

Filter by ODD, robot, date, or severity; drill into single runs; export PDF reports for audits.

⚡ Toward Real-Time

Lightweight pipeline variant that warns when COD approaches or leaves ODD during operation.

In its current form, ODD Observer shows that a small set of focused agents, grounded in ODD/COD knowledge and fed with real robot data, can reconstruct the COD of a Go2 run and compare it to the design ODD in a structured, understandable way.
